## 一、30 秒总开场

> 基于 RAG 的中文财报问答系统。核心建设是 **LLM-Wiki 知识层**——把财务口径知识从代码硬编码和概率性检索中剥离，做成可编译、可治理、fail-closed 的四类知识资产。围绕这个知识层，我完成了三层能力辐射：**知识驱动的检索融合**（量纲修复 + 题型加权）、**数据驱动迭代的地基**（阶段归因工具）、**性能与工程化**（索引常驻、并行检索、并发修复、服务化）。最新一块是 **Agentic 自适应检索 v2**——知识层驱动的反思式检索循环：感知缺口、选择策略、双粒度补检、收敛判定、运行经验反哺知识资产。全程测试驱动：**487 个测试，每次改动零回归**。

## 二、核心叙事主线

**一句话主线**：「这不是一堆优化的堆叠，是**以知识层为核心的能力辐射**——知识资产不只管答案口径，还驱动检索权重、补检决策、停止条件，最后连自己的进化都由运行经验驱动。」

```
纯 RAG 的口径失败 → LLM-Wiki 知识层（四类资产 + 治理）
→ 能力辐射①：知识 → 检索参数（A1/A4）
→ 能力辐射②：知识 → 检索决策（Agentic v1/v2）
→ 地基：归因工具（F3）+ 性能（A2）+ 工程化（D1/D3）
→ 闭环：Agentic 的运行经验反哺知识资产（④）
```

被问"介绍下项目"时按这条主线讲 3 分钟；被问任何一个单项时，先回主线定位再展开细节。

## 三、LLM-Wiki 本体

### 3.1 为什么做（问题定义）

纯 RAG 的四个结构性失败：

1. **语义近似检索分不开易混口径**——"归母净利润"和"扣非归母净利润"的 embedding 距离远小于口径差异应对应的距离，top-k 两者混排
2. **文档口径表述不稳定**——同一指标在不同年报里有多种写法，检索无法保证命中正确口径
3. **口径知识要求必然正确，top-k 检索是概率性的**——概率性机制承载不了必然性要求
4. **口径区别根本不在 chunk 里**——年报从不写"扣非和归母的区别"，这类知识在文档外

### 3.2 做了什么（四类正交资产）

| 资产 | 数量 | 管什么 | 例子 |
|---|---|---|---|
| MET- 指标原子 | 12 | 口径判定与拒答 | 标准名/别名/易混口径/取证规则 |
| PLB- 分析剧本 | 5 | 剧本类问题的证据完整性 | 偿债能力剧本 = 必需指标清单 |
| flag 话题契约 | 17 | 查询侧路由 | 覆盖率 35.3%→100% |
| EVT- 事件原子 | 1 | 主体类事实识别 | 法代识别（regex 三级置信） |

### 3.3 治理层（差异化必背）

- **provenance 刻度**：extracted（生产代码迁移，有等价测试）/ inferred（手写），缺省按 inferred——不假装知道来源
- **有效期审计**：知识有失效期，到期审计而非永久有效
- **内容哈希 + 冻结 Generation**：yaml 是源码，运行时只读编译产物；源失步 fail-closed 拒加载
- **生产者不自批**：质检必须异构模型，Builder 不能给自己产出的原子盖质量章

### 3.4 四条架构决策（被问"参考了什么"时的答案）

| 决策 | 对照 |
|---|---|
| 编译而非检索 | RAG over RAG 的活索引问题 vs 确定性查表 |
| fail-closed 拒答语义 | 金融场景错误答案代价 > 拒答代价 |
| 三层 Registry | 编译层/加载层/运行层的职责分离 |
| Builder 永不自批 | LLM 生成内容的质检独立性 |

## 四、五项系统能力（STAR 精要）

### 4.1 A1 融合量纲修复

**S**：rerank 融合公式 `0.7×语义分 + 0.3×向量分` 怀疑有问题。
**T**：定位并修复，且不能引入新失真。
**A**：先实测分数取值范围（与文档假设 0-10 分不符），发现向量分**量纲随上游 fusion_method 漂移**——默认 RRF 模式下是排名倒数和（<0.1 量级），**名义权重 30% 实际约 2%**。修复：两路分数池内 min-max 归一后加权，名义=实际；三个 reranker 类（FlagEmbedding/VLLM/LLM）统一改造。
**R**：15 个融合单测锁定行为（常数池语义、权重边界、场景覆盖）。

**弹药**："这不是静态量纲不一致，是**随配置漂移的动态失真**——默认配置下它只是悄悄变差、不报错。凭假设修 bug 和凭实测修 bug 是两回事。"

### 4.2 A4 题型加权

**S**：修复后权重语义可信，才有条件做差异化。
**A**：融合权重由 `task_type` 路由——定义类语义主导（0.85）、数字类精确词补强（0.50），权重表进 yaml 不进代码，加载期校验、越界 ValueError，文件缺失软回退默认值（软硬失败分级）。
**R**：键覆盖 QueryPlan 全部 8 类 task_type 实测值域。
**弹药**："A1 修 bug，A4 把修复变成知识层和检索层的接口——知识第一次外溢到检索参数。"

### 4.3 F3 阶段归因

**A**：每题按短路树归因到第一个失败阶段：routing/parse 异常 → 该拒不拒（over_refusal）→ 过度拒答 → 无证据作答（ungrounded）→ 引用错误（citation_error）→ 证据对答案错（evidence_mislocalization / generation_error）→ unknown。产出阶段×错误率矩阵 + capability 分桶。
**弹药（诚实点主动讲）**："存量跑分和评测集零对齐，**基线挂 NULL 没有伪造**——工具就绪、首跑卡 API key，没测的数字不说。"

### 4.4 A2 性能（三层修）

| 层 | 改动 | 工程判断 |
|---|---|---|
| 索引常驻 | 自建 LRU（mtime 进键自动失效） | **不用 lru_cache**——按调用键驱逐会把同索引旧 mtime 键挤掉而非最旧索引，且无逐键删除 API |
| 四路并行 | 每路独立降级（失败→空+warning） | 串行回退路径保留异常传播旧语义，开关 `HYBRID_RETRIEVAL_PARALLEL=0` 完整回退 |
| 多查询并行 | 线程预算两层乘积 | 内层 4 固定，外层 `MAX_THREADS//4` |

**R**：验收标准是**并行==串行输出全等（含顺序）**，不是"差不多对"。

### 4.5 D1 并发修复 + D3 服务化

**素材一（最高级加分项）**："我修的并发 bug 被我自己的测试推翻——第一版读写分离锁自测通过，但并发一致性测试在全量跑时间歇性失败：8 线程同时 cold miss 各自通过检查、各自加载，产生不同 payload 对象。**分离锁保证字典操作原子，不保证 check-then-load 业务原子**。改 double-checked locking 整段持锁。教训进 commit message：缓存修复必须测并发 cold miss，仅测读写互斥不够。"

**素材二**："离线装不上 FastAPI（SSL 断连），服务化没挂起——stdlib `ThreadingHTTPServer` 实现同等接口（/qa、SSE、/healthz），业务与 HTTP 解耦，有网换框架业务代码不动。healthz 把知识层 fail-closed 校验状态直接透出——源失步返回 degraded 而不是 ok。SSE 是七阶段伪流式，如实声明不是 token 级真流。"

## 五、Agentic v2（Agent 岗主叙事）

### 5.1 定调

> "知识层告诉系统**什么时候该再检索、往哪检索、用什么粒度、何时停止**——决策依据全部知识化，决策器目前是规则（LLM 决策器是下一步，接口已预留）。"

### 5.2 五环骨架

```
感知 → 决策 → 行动 → 重评估 → 记忆
```

**① 感知（双时机六触发源）**
- 生成前预检三源：原子证据目标未覆盖（OR 语义）/ 剧本必需指标缺证据 / 检索置信度低
- 生成后校验反思三源：口径门禁拒答（metric_caliber_conflict_refused）/ 指标证据不匹配 / 剧本证据不全——来自校验层 flags，语义比预检更准

**② 决策（规则版策略选择器）**：上轮补检有新增证据 → 维持 dense；无新增 → 切 parent 粒度。v3 换 LLM 决策器接口不变。

**③ 行动（双粒度双策略）**
- dense_recall：同粒度定向补检，**排除易混口径标准名**（往易混方向补检只会强化错误证据）
- parent_recall：切页级粒度回溯（child chunk 不全时页级上下文可能有）
- merge 去重键带粒度维度：(sha, page, scope)——child/parent 同页共存，不是重复信息

**④ 重评估（收敛驱动而非轮数驱动）——最有讲头的一环**
> "三个停止条件：缺口闭合（**剧本 required_metrics 全覆盖即收敛——停止条件是知识说了算，不是跑 N 轮碰运气**）；无新增证据（先切粒度重试一轮，两种粒度都无新增才真收敛）；预算耗尽。外加查询幂等停。补检后**重新生成重新校验**——try-then-closed：口径冲突时补检找到本口径证据就作答，仍只有易混口径才维持拒答。**拒答是底线不是默认**。"

**⑤ 记忆（trace 反哺知识资产——独家性最强）**
> "补检的运行经验积累成知识层进化建议：命中率 ≥80% 的词建议扩进 aliases（查询侧预展开命中即免一轮补检）、零命中的 evidence_target 建议复核表述（文档可能从不这么写）。**只出建议不自动改库**——人工确认后走 yaml 编辑 + 重编译 + 等价测试守护。系统在改进自己的知识，但改不改由人说了算。"

### 5.3 闭包重入（实施硬骨头，备好细节）

- get_answer_for_company 的 140 行生成段（grounding→no_context 早退→生成分支→组装→校验）包进 `_generate_and_validate(current_results)` 闭包，补检后以新证据池重走全链
- **只重跑生成不重跑表格取证，数字题闭环语义不完整**——落地方案时发现的设计修正
- 机械改造用脚本：占位符保护对外字段名 + 全段缩进 + 变量改名；三类误伤（早退 return 漏改/方法名误替换/kwarg 名误替换）被 458 个测试当场炸出

### 5.4 「这算 Agentic RAG 吗」——诚实定位（v2 后升级版）

> "v1 时我会说它严格来说是 adaptive retrieval——单轮、预检、规则。**v2 之后循环形态完整了**：生成后反思触发、行动后重评估、多轮迭代到收敛、多策略行动——完整的感知-决策-行动-重评估循环，只是**决策器是规则不是 LLM**。我接受'规则驱动的反思式检索'这个称呼。没换 LLM 决策器两个原因：一是卡 API key 没法验证收益；二是垂直领域**决策依据的知识化比决策器的智能化更根本**——裸 agent 循环人人会写，agent 在财报场景凭什么判断证据够不够才是坑。接口已留好，换 LLM 决策器是增量工作。"

## 七、深挖 Q&A（按主题分组）

### 7.A 系统设计与架构

**Q：为什么选 RAG 不选微调/SFT？**
> 三个理由：口径知识要**必然正确且可审计**——模型权重里的知识既不可审计也不可即时更新，知识层 yaml 改一行重编译即生效；财报文档每年更新，RAG 的证据可以随文档换而知识层不动；拒答语义要求知道"自己不知道什么"，检索证据缺失是显式信号，参数化知识没有。做过 SFT 样本构造的深度分析（有归档），结论是 SFT 适合改表达风格，不适合承载口径事实——事实进权重后连"它为什么这么答"都无法归因。

**Q：为什么不用 GraphRAG？**
> GraphRAG 解决的是"跨文档全局性问题需要实体关系图"——财报问答的主要失败不在跨文档推理，在**同文档内的口径精确性**。图谱抽取本身是概率性的，把概率性抽取放在必然性要求的前面是方向错误。我的知识层本质上是**人工校验过的、领域特定的迷你知识图谱**（原子间有 confusable_with 关系），只是不做自动图抽取。

**Q：双层架构怎么分工的？**
> 文档证据层负责"证据在哪"（检索、rerank、grounding——概率性，允许近似）；知识层负责"什么是对的"（口径判定、拒答、完整性——确定性，不允许近似）。**概率层永远不能覆盖确定性层**：检索再自信，口径门禁说拒就拒。

**Q：知识层为什么用编译（确定性查表）不用检索（RAG over RAG）？**
> 三个原因：活索引问题（知识库自己也要检索就有自己的召回失败，失败套失败）；延迟（查表 O(1) vs 再跑一遍检索）；可审计性（编译产物可 diff、可哈希、可版本化，检索结果每次不一样没法审计）。longest-match 索引解决多原子命中歧义，dict 顺序敏感问题修过并留了测试。

**Q：为什么规则不全用 LLM（比如让 LLM 判口径）？**
> 判口径这个动作本身要求 100% 正确，LLM 判口径会引入新的概率性——用概率机制守护必然性要求是自相矛盾。我的分工：**规则做判定（零错误容忍），LLM 做表达**（生成、改写——有校验兜底）。Stage E 的异构质检约束也是这个逻辑：质检模型和生成模型必须异构，否则质检是自批。

**Q：fail-closed 为什么优于 fail-open？误拒太多用户体验怎么办？**
> 金融场景错误答案的代价（误导决策）远大于拒答代价（用户换个问法）。但 fail-closed 不是躺平拒答——**try-then-closed 就是给拒答加补救通道**：先补检重生成一次，仍不行才拒。误拒率本身有归因工具盯着（over_refusal 分支），数据驱动地放宽而不是拍脑袋放宽。

**Q：如果服务挂了/知识层加载失败怎么办？**
> 分级：知识层源失步 → 编译产物冻结 Generation 仍可用（降级到旧知识，healthz 透出 degraded）；编译产物也坏 → fail-closed 拒服务而不是带着空知识层瞎答。可用性和正确性的 trade-off 里，这个系统选正确性。

### 7.B 知识层细节

**Q：12 个原子怎么选的？扩到 50+ 的成本？**
> 选择标准：高频 + 易混 + 有明确取证规则（三条核心判据）。12 个覆盖最高频的利润/现金流/偿债指标。扩容边际成本递减：框架、治理、测试基建都是一次性的，新原子主要是领域知识整理（每个 1-2 小时含质检）。**卡的是质检模型 API key，不是人力**。

**Q：原子之间冲突/重叠怎么处理？**
> 两个机制：longest-match 索引（"扣非归母净利润"优先于"归母净利润"命中，解决包含关系的歧义——修过 dict 顺序敏感 bug 并留测试）；confusable_with 显式声明易混关系（归母↔扣非），驱动查询改写排除和补检方向。

**Q：provenance 刻度为什么需要？**
> 知识资产的信任必须有梯度：extracted 从生产代码迁移、有等价测试背书（改一行测试就知道）；inferred 是手写的、只有人工 review。**缺省按 inferred**——不知道来源就按最不可信处理，和 fail-closed 同一哲学。

**Q：冻结 Generation 防的是什么？**
> 防"源码和运行时不一致"：yaml 是源码，编译产物带 Generation 标记，运行时校验失步就拒载。没有这个，会出现"我明明改了 yaml 为什么行为没变"或更糟的"改了 yaml 行为变了但没人知道哪一版在跑"。知识库的版本管理比代码更严格——代码错了测试会炸，**知识错了它只是安静地错误回答**。

**Q：等价测试怎么做的？**
> 迁移 extracted 原子时，等价测试断言新旧实现输出逐字节一致（含边界 case）；这样迁移本身是零行为变化的纯重构，风险和 review 负担都大幅下降。EVT 基线钉死父 commit（BASELINE_COMMIT）防基线漂移——踩过 HEAD 漂移的坑。

**Q：剧本（PLB）和 flag 的区别？**
> flag 管路由（这个问题该走哪条检索路径），剧本管完整性（这类分析必须有哪些指标的证据才算够）。flag 是查询侧的，剧本是证据侧的——剧本的 required_metrics 是 Agentic 收敛判定的知识来源。

### 7.C 检索质量（A1/A4）

**Q：量纲 bug 怎么发现的？**
> 起因是排查另一个问题时看 rerank 分数分布，发现向量路分数全在 0.1 以下——和文档声称的 0-10 分量级不符。追到上游发现 RRF 融合的输出是排名倒数和。**教训：集成第三方分数前先实测分布，文档会过时**。

**Q：为什么 min-max 归一不是 z-score？**
> 三个理由：与检索层既有 `_normalize_scores` 语义一致（同名同语义复用，不造第二套）；池内相对序不变（z-score 会放大离群值影响）；分数本来就是池内相对排序的用途，min-max 语义最贴。**常数池语义**（全同分→1.0）沿用原有约定并锁定测试。

**Q：题型权重 0.85/0.50 怎么定的？拍脑袋？**
> 承认是领域先验 + 快速验证的起点值：定义类问题问的是概念（语义检索强）、数字类问题要精确页码（精确词信号强）。yaml 化的意义就是**起点可以数据驱动地调**——F3 归因矩阵跑起来后按题型错误率调参。诚实说：调参还没跑（卡 key），但调参的接口和依据链路已经通。

**Q：为什么不端到端学一个 ranking 模型？**
> 三个考虑：样本量（财务 QA 标注贵，学不出鲁棒排序器）；可解释性（yaml 权重可以解释给业务方，学出来的黑盒不行）；A1 的教训——**先把启发式做对再做学习式**，启发式错了学习式只是把错误放大。learned ranking 是 v3+ 方向。

### 7.D Agentic（Agent 岗重点）

**Q：多轮循环怎么防失控？**
> 四道闸：预算硬上限（ADAPTIVE_MAX_ROUNDS）；查询幂等停（同查询同策略不重复补检）；收敛条件全部知识化（剧本全覆盖即停——不会自我合理化地"再试一轮"）；**无新证据且两种粒度都试过才停**——不会在单一策略上空转。

**Q：为什么闭环触发放在校验后？预检不都做了吗？**
> 两个都做。预检在生成前（80% 的缺口用 20% 的成本补上）；校验后反思处理预检抓不住的——**口径冲突要等生成+校验才知道**（生成前不知道 LLM 会不会被易混证据带偏）。闭环需要生成段可重入，我把 140 行生成段包成闭包，补检后重走 grounding→生成→校验全链——只重跑生成不重跑表格取证，数字题闭环语义不完整，这是落地方案时发现的设计修正。

**Q：try-then-closed 和无限重试的区别？**
> 严格一次：补检一轮、重生成一次、以二次校验结果为准。**不会循环重试到"答对为止"**——那是在 p-hacking 证据。二次仍冲突就维持拒答（refused_maintained），trace 里如实记录 outcome。拒答是底线不是默认，补救是机会不是执念。

**Q：收敛条件为什么知识化而不是跑固定轮数？**
> 跑 N 轮是**预算驱动**（反正跑这么多），知识化是**目标驱动**（剧本 required_metrics 全覆盖就停）。区别在语义：前者可能早就够了还在跑（浪费）也可能不够就停了（欠检索）。而且知识化收敛可审计——trace 里 gap_closed 是显式字段。

**Q：parent/dense 切换的依据是什么？为什么不直接每次都双粒度？**
> 切换依据是上轮边际收益：dense 有新增就继续（有效不换），无新增才切 parent（低置信的第二手段）。每次都双粒度是**用 2 倍延迟买不需要的证据**——粒度切换是 fallback 不是默认。merge 键带 scope 维度保证双粒度结果不互相挤掉。

**Q：trace 反哺会不会把错误经验写进知识库？**
> 三道防线：建议规则带样本量门槛（≥3 次）和证据计数；只出建议不自动改库；入库走既有 compile 流程，等价测试和门禁全量守护。**系统提建议，人裁决**——和知识层质检的"生产者不自批"同一原则。

**Q：和 Self-RAG/CRAG 的区别？**
> Self-RAG 靠 LLM 自评 token 判断要不要检索（决策在模型里，不可控）；CRAG 用检索质量评估器决定重检索（评估器要训练）。我的差异：**决策依据全部外置到知识层**——要不要补检由原子/剧本的显式覆盖判定决定，不靠模型自觉。垂直领域里，外置知识的决策比模型自省可靠，也便宜（不用额外推理）。

**Q：和 LangGraph/AutoGen 这些 agent 框架比呢？**
> 那些框架解决的是**编排通用性**（图结构、状态管理、工具调用协议）；我的场景是**单域深挖**——状态就一个证据池，动作就检索，图是固定的感知-行动-评估循环。用框架的收益（通用编排）在这个场景换不来什么，成本（引入抽象层、调试黑盒化）倒是实打实。如果将来动作空间扩大（查数据库、调计算器、多文档交叉），会重新评估——**决策器的接口就是为那时留的**。

**Q：为什么不用 function calling 的工具循环？**
> 用了就不是这个形态了——function calling 适合"模型决定调什么工具"的开放式 agent；我的循环是**领域固定的反思结构**（触发源枚举、动作空间两个、停止条件知识化）。开放式循环在金融场景的不可控性（幻觉工具调用、无限循环）正是我要避免的。形态选择服从场景约束，不服从技术时髦度。

**Q：Agentic 循环的延迟开销多大？**
> 单轮补检 = 1 次检索召回（无 rerank）+ 1 次 rerank + 1 次生成。默认关闭（ADAPTIVE_RETRIEVAL_ENABLED=0）按需开——**高价值问题（数字题/剧本题）值得多花 2-4 秒换正确率，闲聊类不值得**。这也是为什么不做成全局默认：开销和收益按题型分布，规则里已经体现。

**Q：如果给你 API key，你第一件事测什么？**
> 有优先级：先跑 F3 归因矩阵拿基线（一切改进的参照系）；再开 Agentic 跑对比（拒救率 = 补检后从拒答变正确答案的比例、轮次分布、每轮边际收益、try-then-closed 两分支占比）；最后按题型调 A4 权重。**先测量再优化**——这个顺序不能反。

**Q：v3 的 LLM 决策器会怎么设计？**
> 接口已预留：RetrievalGap 是结构化 dataclass（trigger/queries/rationale/strategy），规则版 `_choose_strategy` 换成 LLM 版只需替换决策函数、循环骨架和收敛判据不变。LLM 的增量价值在**复杂触发源的组合判断**（多缺口优先级）和**查询改写的语义泛化**（规则只能枚举原子里的词）。LLM 决策的输出仍走同一个结构化接口——**模型可以换，契约不能变**。

**Q：感知层为什么不直接看最终答案对不对？**
> 看答案对不对需要标准答案（评测场景）或另一个判定器（生产场景引入第二个概率源）。我的感知信号全部来自**中间产物**（检索覆盖率、校验 flags）——不需要 ground truth 就能自检，这是它能上生产的前提。

### 7.E 评测与迭代（F3）

**Q：归因树为什么这样分？为什么是短路？**
> 分类学的原则：**每题归因到第一个失败阶段**——后面的失败是前面的下游，全记会把一个 root cause 算成多个阶段的问题。短路保证 root cause 唯一性，修复才有明确的靶子。八分支覆盖：pipeline 异常 / 拒答策略 / 无证据作答 / 证据错位 / 引用错误 / 答案错——每支对应不同的修复 owner（检索/知识层/生成/校验）。

**Q：为什么不直接看准确率？**
> 准确率是结果指标，回答不了"为什么错"和"该修哪层"。归因矩阵是过程指标——**数字掉了能立刻定位是检索塌了还是拒答策略保守了**。两者互补，但迭代节奏由过程指标驱动。

**Q：capability 分桶怎么分？**
> 按知识资产分（口径类/剧本类/主体类/普通类）——桶和知识层的资产类型对齐，这样"某桶掉分"直接映射到"哪类知识资产要补"，指标和资产之间没有翻译损耗。

**Q：评测集零对齐怎么解决？为什么不先对齐？**
> 对齐需要跑分（卡 key），工具先行没有错——工具和基线记录全部就绪，拿到 key 半天出数。挂 NULL 不伪造是底线：**跑分记录里没有的数字，一个都不说**。

**Q：怎么证明你的修复有效（而不是波动）？**
> 三层证据：行为级单测锁定（每个修复有专项测试）；等价性验收（并行==串行全等）；回归零损失（每次改动全量 487 跑一遍，失败集和基线完全一致）。端到端效果层等 key 跑对比——机制证据和效果证据分开陈述，不混着说。

### 7.F 性能与工程（A2/D1/D3）

**Q：为什么不用 Redis 做索引缓存？**
> 缓存对象是**进程内反序列化后的索引结构**（几十 MB 的对象图），Redis 存的是序列化字节——每次取回还要反序列化，恰恰是要省的开销。进程内 LRU + mtime 失效在单机场景是对的粒度。多实例共享索引是另一个问题（到时候考虑 mmap 或只读副本），不为未来架构付现在的复杂度。

**Q：线程 vs 进程 vs 异步，为什么选线程池？**
> 负载是 **IO 密集**（embedding 服务调用、BM25 查询的 GIL 释放段）——线程够用且和现有同步代码零改造。异步要全链路 async 化（改动面大收益重叠）；多进程的序列化开销在进程内共享索引的场景反而倒退。**先测量瓶颈再选并发模型**，不是反过来。

**Q：ThreadingHTTPServer 的局限？什么时候必须换？**
> 局限明确：每连接一线程（几百并发就线程爆炸）、无中间件生态、无 ASGI。换的触发条件：QPS 上生产量级或需要 websocket/token 级真流式。业务和 HTTP 已经解耦（QaService 不依赖任何 HTTP 类型），换框架是适配层重写不是业务重写——这是当时设计的主要目标。

**Q：GIL 之下为什么还要 double-checked locking？**
> GIL 保证字节码原子，**不保证 check-then-load 复合操作原子**——两个线程的两次 check 都在对方 load 之前执行是完全可能的调度序列（我的测试真的复现了：8 线程 cold miss 产生不同 payload 对象）。GIL 防的是数据竞争，不防 TOCTOU。

**Q：服务无状态吗？水平扩展怎么做？**
> 无状态（知识层只读编译产物 + per-request 局部 state——D1 教训后 Agentic 的预算池也是局部 dict 不进实例属性）。水平扩展 = 多实例 + 前置负载均衡，唯一共享态是日志（trace 反哺是离线分析，天然解耦）。

**Q：SSE 伪流式是什么？为什么不真流式？**
> 七阶段事件（检索/重排/grounding/生成/校验的进度标记）——阶段间是原子的，阶段内不流。真 token 流式需要生成模型 stream 接口 + 校验后置的架构改动（校验必须看完整答案才能判口径），**为了体感牺牲校验前置不划算**——如实标注"伪流式"不冒充。

### 7.G 工程过程

**Q：487 个测试怎么组织的？**
> 三层：行为单测（每个功能专项文件，如 test_adaptive_retrieval 31 例）；等价/回归测试（迁移等价、并行串行全等、基线钉死 commit）；集成冒烟（服务层 12 例含并发隔离）。**机械改造（闭包重入）靠全量跑兜底**——三类误伤全是它炸出来的。

**Q：机械改造怎么保证正确？**
> 脚本化（缩进/改名/占位符由脚本保证一致性）+ assert 锚点计数（防重复写入）+ 字节级回读校验 + 全量测试。占位符只保护了字段名、漏了方法名和 kwarg 名——**教训：正则替换的盲区靠测试网兜住，不靠人眼**。

**Q：commit 怎么切的？**
> 按验收单元切：每个 commit 自带行为锁定测试 + 可复制的验收命令；方案文档和实施结果分离成两个 commit（方案先行、结果回填）。commit message 记录**实施中推翻方案假设的地方**（比如 S5 抓到的收敛矛盾）——这些是未来 review 时的路标。

**Q：如果重来一遍会改什么？**
> 三个：闭包改造直接脚本生成后先跑测试再手修（我修了三类误伤才意识到该先跑）；知识层治理（provenance/Generation）应该从第一个原子就上而不是迁移后补——补的成本是重跑全部等价测试；归因工具应该在第一个 badcase 就写而不是优化后期——没有它前期的修复效果全是感觉。

### 7.H 开放与压力题

**Q：项目最大的不足？**
> 诚实排三个：端到端量化证据缺失（卡 key，机制就绪数字空白——面试里我主动说这个）；原子覆盖面（12 个是框架验证规模，生产要 50+，卡质检模型）；决策器是规则（v3 方向明确但没实施）。**每个不足都带下一步**——不足本身不可怕，没有下一步的不足才是。

**Q：12 个原子是不是太少了？**
> 是框架验证规模的诚实数字。价值的证明不在数量在机制：治理（provenance/Generation/不自批）、测试（等价迁移）、扩容成本曲线（边际递减）都在 12 个上验证过了。**少而可信 > 多而失控**——知识层的意义就是让"扩到 100 个"不失控。

**Q：为什么不用 LlamaIndex/LangChain 现成框架？**
> 用过其中的组件级思想（混合检索、rerank），但整框架的抽象和我的需求错位：知识层的 fail-closed 门禁要**侵入校验链**（框架的 pipeline 抽象不暴露这个位置）；Agentic 循环要生成段可重入（框架把生成封装死了）。框架适合快速搭原型，**深度定制时抽象层变成阻力**——自己写的每一行都能改到语义级。

**Q：给你一个新的垂直领域（法律/医疗），怎么迁移？**
> 迁移的是**方法论不是知识**：先做失败模式分析（对应四类结构性失败）→ 定义正交知识资产类型（法律可能是法条原子/判例剧本/管辖 flag）→ 治理三件套（provenance/Generation/不自批）第一天就上 → F3 归因树按新领域的阶段重画 → Agentic 的五环骨架（感知/决策/行动/重评估/记忆）结构不变、触发源和策略重定义。**框架代码复用率估计 60%+，知识资产从零**——这正是知识层和代码分离的红利。

**Q：这个项目的商业价值？**
> 财报问答的准确率天花板决定产品形态：90% 可以做辅助工具，99% 才能做决策入口。纯 RAG 卡在口径类问题（易混口径混排是结构性的），知识层把这一类从"随机对错"变成"确定性对或确定性拒"——**拒答可运营（引导换问法），错误答案毁信任**。Agentic 再把一部分拒答转成正确答案。价值链：口径可信 → 拒答可控 → 补救有效。

**Q：你个人贡献的边界？（是否团队项目）**
> 如实回答按实际情况调整：架构设计、知识层全链、五项优化、Agentic v1/v2、全部测试基建是主导；依赖的外部条件如实说明（API key 限制、离线环境约束）。**把"我做的"和"环境限制"分清楚说**——边界清晰反而加分。

**Q：什么是你被问倒也不慌的？**
> 没跑过的数字、没实施的方向（LLM 决策器、learned ranking）——都主动归到"卡 key 待验证"和"v3 规划"。**慌的应该是假装知道**：我的口径里每个数字都有测试背书，每个"不知道"都有下一步。

## 八、连环追问链（模拟面试官顺藤摸瓜）

**链 1：从开场往下挖**

Q：你说"概率性机制承载不了必然性要求"，那你的检索层不也是概率性的？
> 对，所以架构上**概率层永远不覆盖确定性层**：检索排序再自信，口径门禁按知识层规则判定，该拒就拒。我从不试图把检索做到 100% 准——我把"检索不准"当作常态，让知识层兜底。

Q：那知识层自己怎么保证 100% 准？
> 不保证，它保证**可审计**：每个原子的 provenance（extracted 有等价测试 / inferred 有人工 review）、内容哈希、冻结 Generation。错误会被发现而不是被隐藏——这就是我能给出的最强保证。声称 100% 正确的知识系统反而不可信。

Q：inferred 原子错了怎么办？
> 三层发现机制：Stage E 对抗质检（异构模型）在入库前拦；F3 归因在运行中发现（某原子关联题系统性错误会显形）；有效期审计强制定期复核。发现后的修复走 compile --update，等价测试保证不引入新问题。

**链 2：从 Agentic 往下挖**

Q：补检的查询词是哪来的？
> 从触发源的知识载体生成：evidence_gap 用原子的 evidence_targets（排除 confusable_names——不往易混方向补）；playbook_incomplete 用缺失指标的 standard_name。**查询词不是 LLM 即兴生成，是知识资产的字段**——可枚举、可审计、可被 trace 反哺优化。

Q：为什么补检走纯召回（hybrid 无 rerank）而不是全链？
> 补检目标是**查全**不是排准——缺口本来就是"当前 top-k 没有的证据"，再走一遍同样的 rerank 大概率还是把它排下去。纯召回拿回候选池，交给全量 rerank 在更大的池上重排。

Q：rerank 会不会把补检拿回的证据又排出去？
> 会有这个风险，两层缓解：merge 后的池全量 rerank（补检证据和原证据公平竞争，如果它真的相关，rerank 会留它）；top_n 取 debug_top_n 而不是 answer context 的窄窗口，减少边缘证据被截。这是当前设计承认的局限——极端 case 下补检证据进池但没进 context，trace 的 new_hits 字段能发现这种情况。

Q：你说 trace 能发现，具体怎么发现？
> 对比同一轮的 new_hits（补检拿回多少）和 gap_closed（缺口是否闭合）：new_hits>0 但 gap_closed=false，就是"证据拿回来了但没用上"——要么 rerank 排掉了，要么证据其实不相关。分析脚本按原子聚合这个模式，高频出现的原子就是靶子。

**链 3：从 A1 量纲往下挖**

Q：min-max 归一对离群值敏感，一个极端分会压扁整个池，你处理了吗？
> 处理方式是承认它：融合的用途是池内排序，离群值压扁其他分数的相对间距时，说明该路信号本身分布异常——归一后权重仍按名义比例生效（这是修复的目标），排序质量是 rerank 的职责不是归一化的职责。**先修量纲失真（30% 变 2% 的大问题），分布细病是下一层**——修复要分层，一口吃不成。

Q：那 LLM 路分数的分布你测过吗？
> 测过才敢动 fuse：LLM rerank 分数是模型输出的相关性评分（0-10 段），分布相对稳定；向量路的问题恰恰是分布**随 fusion_method 剧烈漂移**（RRF 下 <0.1）。两路都实测分布是这次修复的前置动作。

**链 4：从 D1 并发往下挖**

Q：double-checked locking 里第一层 check 不加锁读，会不会读到半初始化对象？
> Python 层面不会——对象引用的赋值是原子的，读者要么看到 None 要么看到完整引用，不存在半对象。竞态点只在**多个线程同时通过第一层 check**（都看到 None 都去 load），第二层锁内再 check 保证只有一个线程真正加载。C++ 那种 memory reorder 问题在 GIL 的语言里不存在，但 TOCTOU 依然存在——我的测试证明的就是这个。

Q：load 很慢（几十 MB 索引），持锁会不会阻塞其他读请求？
> 会——这是 deliberate trade-off：cold miss 场景下阻塞换取"只加载一次"，比 8 个线程各自加载 8 份（内存×8、加载×8）便宜。热路径（cache hit）走无锁快路径不受影响。

**链 5：从 F3 归因往下挖**

Q：归因到 generation_error 的题，你怎么区分是模型能力问题还是 prompt 问题？
> 归因矩阵不区分这么细——它告诉你"钱该花在生成层"，层内归因靠另一个维度：抽 examples 看 error mode 聚类（数字幻觉/口径混用/单位错误是不同问题）。**工具定位层次，人定位根因**——我不假装一个工具解决所有粒度。

Q：over_refusal 和 ungrounded_generation 同时高怎么办？
> 这两个互为镜像（一个太保守一个太放），同时高说明**判定标准本身有问题**而不是策略问题——优先查口径门禁的规则（阈值、证据判定条件），而不是左右调拒答率。这是归因矩阵的联动诊断价值：单指标会误导，指标组合才是信号。

## 九、代码细节级问题（证明你真的写了代码）

**Q：_generate_and_validate 闭包捕获了哪些变量？为什么用闭包不用传参？**
> 捕获请求上下文的只读变量（question/schema/company_name/rewrite_result/route_info 等），证据池是唯一参数 current_results。用闭包是因为这些变量在闭包定义点已求值，重入时不需要重新构造调用栈——**重入单元的输入只有会变的东西（证据池）**，不变的东西闭包捕获，边界清晰。

**Q：_merge_key 为什么要 scope 维度？默认值是什么语义？**
> (sha, page, scope)：child chunk 证据和 parent 页级证据是不同信息（chunk 是片段、页是完整上下文），同页共存才对。scope 缺省 child——与 retrieval.py 的 result_scope 语义一致，**跨文件的同名概念必须同语义**，这是我在 reranking 的 _minmax_normalize 上吃过甜头（发现两文件同名同语义直接复用）后立的规矩。

**Q：_choose_strategy 为什么不看 round_index 了？**
> 看过，被测试推翻了：切粒度重试轮不消耗 rounds_used（无新增不计轮），按轮数判"首轮"会永远卡在 dense。现在只看 prior_evidence_gain，首轮的 dense 由 state 缺省值（True）保证。**这个坑是 S5 端到端测试跑出来的，commit message 里记了全过程**。

**Q：adaptive_state 为什么是局部 dict 不放实例属性？**
> D1 的教训泛化：processor 实例是多线程共享的，实例属性会串请求状态（A 请求的补检轮数泄漏给 B 请求）。局部 dict 随调用栈生灭，天然隔离。**并发安全不是修一处，是把教训变成模式**。

**Q：POST_VALIDATE_TRIGGERS 为什么只映射三个 flag？**
> 只映射"可由补检补救"的：口径冲突/证据不匹配/剧本不全——补检可能改变结果。其他 flag（如 numeric_grounding_weak）补检救不了，映射了就是空转。**触发源枚举的原则：每个触发源必须对应一个有效的行动**。

**Q：detect_post_validate_gap 里 flag 有触发源但原子未命中为什么要 continue 不是返回 None？**
> 因为 flags 是列表——这个 flag 救不了，后面的 flag 可能救得了。continue 跳过当前继续找，return None 是整个放弃。多触发源场景下这是优先级链。

**Q：_IndexCache 的键为什么带 mtime？**
> 自动失效：知识层/索引重建后 mtime 变，旧键自然 miss 重新加载——不需要显式 invalidate API（lru_cache 也给不了）。同路径旧 mtime 的键在 get 时顺带清理，防驱逐错对象。

**Q：SSE 七阶段是哪七个？为什么是这个切法？**
> 请求接收/重写/检索/重排/grounding/生成/校验——按**用户可感知的等待段落**切（不是按代码函数切），每段一个事件让前端能渲染进度。阶段粒度是体验设计不是技术分层。

## 十、LLM 基础与项目结合

**Q：embedding 用什么模型？为什么？**
> 项目用的 BGE 系列中文模型（检索层既有配置）。选型逻辑：中文财报语料的 SOTA 开源、dense/sparse 双路都覆盖。**我没有为选型重新跑对比（成本不允许），但我做了选型之后该做的事**——量纲修复保证两路分数公平融合，这比换模型收益更确定。

**Q：chunk 策略怎么定的？双粒度是什么？**
> child chunk（语义段）管精确检索，parent（页级）管上下文完整——检索命中 child、生成用 child+parent。这个结构直接启发了 Agentic 的双策略：dense 同粒度补检、parent_recall 切粒度回溯。**架构决策会跨层复用**。

**Q：rerank 用的什么？LLM rerank 和 cross-encoder 的取舍？**
> LLM rerank 为主（和生成模型同源，语义对齐）+ 向量距离做融合信号。cross-encoder 更快但需要训练对（财务领域标注贵）；LLM rerank 零训练接入，代价是延迟——用 batch 融合（一次调用评多个候选）摊薄。取舍框架还是：**先零训练方案跑通，标注数据攒够了再上学习式**。

**Q：生成的温度/参数怎么设的？拒答和温度有关系吗？**
> 数字类低温（一致性优先），分析类适度。拒答和温度无关——拒答是校验层的确定性判定，不是模型自我评估。**把不确定性关在参数里，把确定性放在架构里**。

**Q：为什么不用 CoT 让模型自己推理口径？**
> 口径判定是查表问题不是推理问题——CoT 推理"扣非是否等于归母"只会更自信地错。CoT 适合多步推导（剧本类问题的跨指标分析），不适合事实判定。**工具按问题性质选，不按流行度选**。

## 十一、行为面试题

**Q：讲一次你和（自己/方案）意见不一致的经历**
> 最好的素材：我的 v2 方案里收敛条件 2 写的"无新增即停"，和策略切换"无新增切粒度"自相矛盾——实施时 S5 端到端测试跑出来，无新增 break 后永远到不了切粒度的下一轮。**方案是我写的，测试不认我是作者**。当天修正控制流（dense 无新增先切 parent 重试）并把全过程写进 commit message。我对"被自己的产出打脸"的态度：这是测试驱动开发的日常，不是事故。

**Q：怎么在不确定信息下做决策？**
> 两例：FastAPI 装不上（环境不确定会不会修好）→ 解耦设计让"等环境"和"推进业务"并行；API key 一直没到（不确定何时到）→ 把所有能离线做的（工具、基线记录、测试）做完，key 到了只剩跑数。**不确定性下推进确定性的部分**，而不是停下来等。

**Q：一次需要快速学习新东西的经历**
> Agentic RAG：从"这不就是多检索一次"的轻视开始，读 Self-RAG/CRAG 论文后发现核心问题是**停止条件和决策依据**——然后把自己方案的决策依据全部锚到知识层。学习闭环：论文给形态、自己的场景给约束、测试给验证。

**Q：优先级怎么排的？（A1-F3-D1-D3 一堆事）**
> 排序原则三条：正确性 > 性能 > 体验（金融场景的代价排序）；有 bug 先修 bug（A1 是失真，其他都是在失真地基上盖楼）；数据地基先于数据消费（F3 归因先于一切"优化效果"的宣称）。这个排序让我在 9 个功能 commit 里没有一次返工。

**Q：最有成就感的时刻？**
> D1 的测试间歇性失败复现那一刻——flaky test 大多数人会选择重跑掩盖，我追了下去发现是自己的锁设计错了。**比自己写对更进一步的，是证明自己写错过**。
